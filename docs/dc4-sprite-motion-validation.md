# DC4 / DC4 Plus Harmony sprite motion

The recorded Nino and Sorane differences came from shared engine behavior.
Arisa32 replaced queued movements with one guessed offset, ignored dialogue
gestures, and executed delayed expression commands immediately. The corrected
implementation follows the native position queue and dialogue event scheduler.

The investigation uses `apaini.avi` and `apainiarisa32mp4.mp4` from the user's
Downloads folder, the installed DC4 and PH executables, and the phone's copied
MES patch. The scene is `dc4_mia20190315c.mes`, available in Scenario under Nino,
page 4, first entry, `これからもよろしく`.

## Recording evidence

The PC clip contains 318 decoded frames. Its AVI header reports 343, so frame
number divided by 30 is not a reliable timestamp. The Arisa32 clip contains
569 decoded frames and has variable frame intervals. Comparison uses decoded
presentation timestamps and aligns each dialogue independently.

| Observation | Native PC recording | Old Arisa32 recording |
| --- | --- | --- |
| Nino, starting PC frame 226 / Arisa frame 277 | Two upward movements, returning to baseline between them | One short residual movement; second movement absent |
| Nino peak displacement | About 11 recording pixels upward, consistent with 10 game pixels at 1360/1280 scale | About 3 recording pixels upward at the first captured frame, then baseline |
| Sorane, starting PC frame 130 / Arisa frame 82 | Horizontal displacement reaches approximately +9 and -9 recording pixels | No horizontal displacement in the tracked interval |
| Sorane expression | `SOR_A1_A08` throughout the recorded line | `SOR_A2_A01` appears immediately |

Nino template references are PC frame 260 and Arisa frame 370. Sorane uses a
different reference within each recording, PC frame 180 and Arisa frame 200,
because the poses differ. Correlation is at least 0.985 in the plotted dialogue
intervals. Pixel offsets are normalized by 1360/1280 for PC and 856/1280 for the
Arisa32 viewport. These measurements establish direction, amplitude, stage
count and the expression mismatch. Capture gaps and click timing prevent a
claim of exact wall-clock agreement between the two videos.

Local evidence is under `build/sprite-motion-audit/`: tracking CSVs retain every
decoded frame, `sorane-evidence.jpg` shows the pose mismatch, and
`motion-comparison.png` compares the recordings with the corrected C++ engine.
The engine series is generated by the integration test, not a new phone recording.

## Native semantics and changes

| Path | Recovered behavior | Implementation |
| --- | --- | --- |
| `0x8E` position | Signed w0/w1; slot from w2; bit 0x40 uses the saved batch origin. Duration is w3 times 6 frames, with zero meaning 60. | Queue up to 100 stages instead of replacing the previous stage. Preserve the final target and omit zero-distance stages. |
| `0x8E` wave | Mode bit 0x20 configures duration/axis; bit 0x10 queues amplitude and angle endpoints for the selected slot. | Independent sine/cosine queues for horizontal and vertical movement. |
| `@bt1..4`, `@by1..4` | Vertical/horizontal positions +8, 0, -8, 0, each over 10 frames. | Execute the four stages on the addressed slot. |
| `@tN` | N times 100 ms for the next event; then reset the explicit delay. | Schedule events relative to dialogue start, using native text-speed timing when no explicit delay is supplied. |
| `0xB0`, `@dN`, `@cmdN` | Collect command batches, then execute group N-1 at the event time. | Defer the collected image/transform commands. Advancing or skipping settles pending batches. |
| `0x8B` entrance modes 0/1/2 | Fade in over 12 frames; modes 1/2 start 20 pixels left/right of the final position. | Fade and position interpolation with the native setup tick. |
| `0x8C` simple entrance | Effect slot 12; 6 frames for side entrances, 20 for alpha-only entrance. | Use the same movement machinery; reset fade state when a fade-out interrupts an entrance. |
| Snapshot persistence | Pending motion and expression events must survive a pause/load. | Snapshot v11 stores queues, clocks, alpha state and delayed commands. Validate saved command offsets against actual MES boundaries. |

Native DC4 references: dispatcher `0x42DA46`, position enqueue `0x4474C0`,
queued-target getter `0x4442E0`, position setup tick `0x449194`, horizontal wave
`0x447620`, vertical wave `0x447700`, dialogue parser `0x41FD70`, event executor
`0x4320B0`, and B0 handler `0x428DC3`. PH's corresponding 0x8E dispatcher is
`0x42D8B6`. Disassembly excerpts are retained in the local audit directory.

In this scene, Nino receives `(0,-10,64,1)`, `(0,0,64,2)`, then those two stages
again. The four stages take 40 native ticks including setup ticks. The fourth
operand is a duration, not an animation ID. Sorane's `@by2@t50@d1` starts the
horizontal gesture immediately and executes the expression batch at 5,000 ms.
The PC recording advances the line before that deadline; line advance also
settles the pending batch.

DC4's original version of this line uses `@by2@t45@d1`, giving a 4,500 ms
expression delay. PH uses 5,000 ms. The motion sequence is shared, but the
authored delay differs between the two game editions. The integration check
uses each edition's actual delay.

## Other characters and patch comparison

The full scan includes 511 DC4 MES files, 536 PH files and 495 phone patch files,
with no decode failures. Counts are static script occurrences, not gameplay
coverage or executed-event counts.

| Command | DC4 | PH | Phone patch |
| --- | ---: | ---: | ---: |
| `0x8B` | 30,491 | 33,215 | 33,213 |
| `0x8C` | 657 | 681 | 681 |
| `0x8E` | 13,045 | 15,594 | 15,594 |
| `0x8F` | 0 | 0 | 0 |

For every filename shared by PH and the phone patch, the ordered
`0x8B/0x8C/0x8E/0x8F` operand sequences are identical. The copied base and patch
versions of the recorded MES also have the same SHA-256:
`dadc82ee7fa153c5e565e542458fdd3146d56ac6ad2702c65907d78646448b3e`.
This excludes changed motion operands as the explanation for this patch's
recorded discrepancy. Other patches can change scripts and must be compared
separately.

Slot-aware scanning finds the same position-command mechanism on `HIY`
(Hiyori), `ALI` (Alice), `SII` (Shiina), `NIN`, `SOR` and other asset prefixes.
Examples and raw operands are in `slot-audit.json`. The scanner tracks direct
slot loads and excludes deferred loads; it does not execute branches, so these
are code-path examples rather than exact per-character occurrence counts.
The correction applies to the addressed sprite slot, without a character-name
special case. Regression fixtures exercise all five position slots in both
DC4 and PH formats.

The regressions also replay these actual DC4 operand examples in both formats:

| Character prefix | Script and code offset | Target displacement | Duration |
| --- | --- | --- | --- |
| `HIY` | `dc4_asa20190430b.mes:14672` | Slot 3, y = -10 | 12 movement frames |
| `ALI` | `dc4_kyo20190204a2.mes:32897` | Slot 0, y = -10 | 18 movement frames |
| `SII` | `dc4_kyo20190204b.mes:4851` | Slot 0, y = +11 | 18 movement frames |

The old mode-3 guess assigned +12 to both `ALI` and `SII`, ignoring their
opposite signed operands. The corrected engine respects the supplied direction,
duration and final position. These tests use copied commands with a controlled
starting position; they do not substitute for recordings of those full scenes.

## Validation and limits

The dedicated regression test covers four-stage movement, all five slots,
signed two-axis targets, relative batch origins, absolute resets, zero-distance
stages, default duration, horizontal/vertical waves, 20 Hz versus 60 Hz updates,
delayed command groups, tag delays, entrance fades, skip, animation disabling,
and mid-animation snapshot restore. An installed-data replay checks Sorane's
first pose at 3,500 ms, her delayed pose at 4,500 ms (DC4) or 5,000 ms (PH),
and Nino's complete queue.

The desktop build completed. The full CTest run passed 25 of 27 tests; the two
failures were fixtures that still labeled a v11 payload as an older snapshot.
The fixtures now validate and remove the idle v11 extension before creating
their v5/v9 saves. After rebuilding, `dc4_sprite_motion_test`, `dc4_effect_test`
and `dc4_message_face_test` all passed (3/3). This retains the checks that the
engine reads old saves and reconstructs their portraits; the production reader
still rejects trailing payload data.

Both installed-data replays passed using `H:/Games/DC4 All Age/AdvData` and
`H:/Games/D.C.4 Da Capo 4 Plus Harmony/AdvData`. Their logs are
`build/sprite-motion-audit/dc4-replay.log` and `ph-replay.log`; each output
directory contains the position CSVs and rendered frames.

Android `assembleDebug` completed for arm64-v8a and armeabi-v7a. The APK is
`android/app/build/outputs/apk/debug/app-debug.apk` (14,297,362 bytes).
SHA-256: `9a8bda20deba1e457e3dfcab0b15c8b70393c6491fa09ca8fc2ecf08788fa3a0`.
This APK has not been installed or recorded on the phone in this validation.
`engine-scenes.png` contains generated C++ frames showing Sorane's initial
and delayed poses and Nino's initial and first peak positions.

Native masked sprite fades remain approximate: `0x8B` kind 3 and masked
fade-out, and `0x8C` kind 3, do not yet reproduce the native per-pixel mask.
The existing effect-layer fade-out uses uniform alpha. No `@bi`/`@bo` or `0x8F`
occurrences were found in this corpus; this change does not implement them.
The recordings cover two characters in one scene. The shared paths have broader
script and regression coverage, but this is not a claim that every animation
of every character has been visually matched to PC.

Snapshot v11 preserves active queues in Arisa32's `.arisa` companion. Standalone
native `.dat` files retain the existing static renderer-state export; live queue
interchange with the PC engine has not been validated here. Older snapshots
remain readable but do not contain the newly introduced pending-event state.
